# MOOtation

*[English](README.md) · **Русский***

**Header-only библиотека на C++17 с 60 алгоритмами многокритериальной и многомерной (many-objective) эволюционной оптимизации, реализованными по оригинальным статьям.**

*MOO* — multi-objective optimization, многокритериальная оптимизация; *mutation* — оператор, на котором стоит каждый из этих алгоритмов. Название — оба слова разом.

Никаких зависимостей, кроме стандартной библиотеки C++. Каждый алгоритм сверялся построчно с первоисточником (псевдокод, формулы, значения параметров по умолчанию); каждое сознательное отклонение и каждое разрешение неоднозначности в статье объявлено в шапке соответствующего файла со ссылками на раздел и формулу.

Два файла не являются переносом статьи и говорят об этом в собственных шапках: `ibea_eplus_clean.hpp` — задокументированная композиция двух опубликованных алгоритмов, а `srv_moead.hpp` — явно экспериментальная экстраполяция SRV на носитель, который статья про SRV не рассматривает.

## Главное

- **60 алгоритмов**: доминирование по Парето, декомпозиция (семейство MOEA/D), индикаторные, на опорных векторах, кластерные и архивные подходы — один `#include`, никакой сборки.
- **Верность источнику как свойство.** Каждый `.hpp` начинается со ссылки на статью (авторы, издание, DOI), краткой схемы цикла поколений, параметров по умолчанию из статьи и явного нумерованного списка отклонений. Библиотека прошла несколько раундов независимого аудита против первоисточников, включая состязательный пересмотр и прогоны под рантайм-санитайзерами (чисто по ASan/UBSan).
- **Геномы:** вещественный везде; 45 из 60 работают также с бинарным и смешанным (вещественный + бинарный). Оставшиеся 15 — только вещественные, потому что таков их оператор воспроизводства (их шапки об этом говорят, а те, что могли молча выбросить бинарный геном, теперь вместо этого отказываются работать).
- **Ограничения:** свёртка нарушений (CV) с обработкой «сначала допустимость» / доминированием с учётом ограничений — во **всех 60**, по умолчанию выключено, как в исходных (безусловных) статьях. Каждая шапка указывает, куда именно подключается обработка ограничений — в недоминируемую сортировку, в скаляризующее сравнение, в фильтр архива, в правило усечения, — потому что правильное место у каждого алгоритма своё и лишь одно из них является настоящим отношением предпочтения этого алгоритма.
- **Диагностика:** некоторые алгоритмы молча подменяют запрошенный параметр — число подобластей, не являющееся достижимым размером решётки, округляется вверх, и вместе с ним меняется производная квота на подобласть. Каждый такой случай объявлен в шапке файла и, через `set_warn_handler`, объявляется ещё и в рантайме. По умолчанию молча.
- **Внешнее / пакетное вычисление:** подключите свой вычислитель (например, симулятор) через интерфейс batch-executor; целевые функции вычисляются лениво.
- **Воспроизводимость:** явное задание зерна (`set_seed`), детерминированные генераторы опорных точек (симплексная решётка Das–Dennis, двухслойная) и значения по умолчанию из статьи везде, где статья их даёт. Где не даёт — часть статей не приводит индекс распределения или приводит его только для одного числа критериев — шапка говорит об этом прямым текстом и называет, что взято вместо. Несколько значений по умолчанию намеренно отличаются от статьи ради единообразия библиотеки; это пронумерованные отклонения, а не молчаливый выбор.

## Какой интерфейс мне нужен?

| ситуация | что использовать | где |
|---|---|---|
| C++, один алгоритм, известный на этапе компиляции | `Optimizer<Ind, Core>` | [Быстрый старт](#быстрый-старт) |
| C++, алгоритм выбирается в рантайме, или цикл вычисления ваш | `mootation::Session` / `run` | [`include/mootation/embed.hpp`](include/mootation/embed.hpp) |
| Python, целевые функции — функция на Python | `mootation.minimize` | [`python/examples/01_basic.py`](python/examples/01_basic.py) |
| Python, стандартные тестовые наборы | `mootation.benchmarks` | [`python/examples/03_benchmarks.py`](python/examples/03_benchmarks.py) |
| Целевые функции считает отдельная ПРОГРАММА (солвер, сеточник, стенд) | TOML + `mootation.run` | [`python/examples/demo.toml`](python/examples/demo.toml) |
| Rust, C#, Julia, R, MATLAB, Fortran, Go | C ABI | [`include/mootation/capi.h`](include/mootation/capi.h), обёртки в [`capi/wrappers/`](capi/wrappers/) |
| Продолжить законченный расчёт или сменить алгоритм посреди исследования | сохранить / засеять популяцию | [`python/examples/06_restart.py`](python/examples/06_restart.py) |
| Нет никакого контроля над путями включения | единый заголовок | [амальгамация](#единый-заголовок) |

Все они дотягиваются до одних и тех же 60 алгоритмов. Разница в том, кто владеет циклом и что пересекает границу, — а не в том, что можно запустить.

## Быстрый старт

```cpp
// nsga2_zdt1.cpp — NSGA-II на встроенной задаче ZDT1
#include <mootation/mootation.hpp>
#include <iostream>

int main() {
    using namespace mootation;

    Problem<NSGAII_Individual>   prob;               // по умолчанию: ZDT1, n=6
    DataVault<NSGAII_Individual> vault(100, prob);   // размер популяции 100

    // Именно `defer_setup` делает расчёт воспроизводимым. Конструктор с одним
    // аргументом вызывает setup() из своего тела, а тот сразу разыгрывает
    // начальную популяцию — после этого set_seed() уже ни на что не влияет.
    Optimizer<NSGAII_Individual, NSGAIICore<NSGAII_Individual>>
        opt(std::move(vault), defer_setup);

    opt.get_algorithm().set_seed(12345);
    opt.setup();

    opt.optimize(500);                               // 500 поколений

    auto& v = opt.get_vault();
    for (std::size_t i = 0; i < v.active_n(); ++i) {
        const auto& f = v.objectives_of(i);
        std::cout << f[0] << ' ' << f[1] << '\n';
    }
}
```

```bash
g++ -std=c++17 -O2 -Iinclude examples/nsga2_zdt1.cpp -o nsga2_zdt1 && ./nsga2_zdt1
```

### Встраивание в свою программу

Когда значения целевых функций приходят оттуда, куда оптимизатор не может обратиться сам, — из симулятора, процесса-солвера, измерительного стенда, другого языка, — крутите цикл сами. `ask()` выдаёт кандидатов, `tell()` принимает значения их целевых функций и возвращает следующих кандидатов.

```cpp
#include <mootation/embed.hpp>

mootation::Session s(mootation::Settings::from_file("run.cfg"));

std::vector<std::vector<double>> F;
for (auto X = s.ask(); !X.empty(); X = s.tell(F)) {
    F.assign(X.size(), std::vector<double>(s.n_objs()));
    for (std::size_t i = 0; i < X.size(); ++i)
        F[i] = my_simulator(X[i]);      // X[i] — переменные одного кандидата
}
mootation::Result r = s.result();
```

**Размер пакета выбирает алгоритм, а не `pop_size`.** Поколенческие алгоритмы отдают целое поколение потомков разом; стационарные (MOEA/D-DE, MOEA/DD, …) отдают по одному кандидату, потому что так эти алгоритмы определены. Размеряйте цикл по `X.size()`.

Если функцию можно просто отдать, циклом владеет `run()` — те же `Settings`, тот же `Result`, побитово одинаковый результат при том же зерне:

```cpp
auto r = mootation::run(settings,
    [](const std::vector<std::vector<double>>& X,
       std::vector<std::vector<double>>& F,
       std::vector<std::vector<double>>& /*G*/) {
        for (std::size_t i = 0; i < X.size(); ++i) F[i] = my_simulator(X[i]);
    });
```

Настройки — обычная структура, и те же поля составляют обычный файл `ключ = значение`: ни схемы, ни билдера, ни реестра.

```ini
algorithm   = nsga3        # любое имя из mootation::algorithm_names()
pop_size    = 92
max_gen     = 300
seed        = 42
n_vars      = 7
n_objs      = 3
lower       = 0            # одно значение распространяется на все n_vars
upper       = 1
constraints = none         # none | feasibility | cdp | eps_constraint
eta_c       = 30           # необязательные ручки без указания берут значение из статьи
```

`examples/run.cfg` — прокомментированная копия всех ключей. Неизвестный ключ — это ошибка, а не молчаливое бездействие: опечатка не должна тихо давать расчёт, отличный от заказанного. Ручка, которой у выбранного алгоритма нет, попадает в `Result::ignored` по той же причине. Ограничения передаются второй матрицей `G` рядом с `F`, по строке на кандидата, значение `<= 0` означает «выполнено».

Поскольку алгоритм выбирается по имени в рантайме, `#include <mootation/embed.hpp>` инстанцирует в этой единице трансляции все 60 — это реальная плата временем компиляции. Программе, которая всегда использует один алгоритм, следует собирать `Optimizer<Ind, Core>` напрямую, как в быстром старте выше. `examples/embed_asktell.cpp` запускает обе формы и проверяет, что они сходятся.

### Запуск против своего солвера (TOML)

Когда значения целевых функций дают программы, а не функция, — сеточник, солвер, измерительный стенд, — опишите расчёт в файле и дайте `mootation.run` его вести. Чистый Python, без зависимостей: `tomllib` входит в стандартную библиотеку с 3.11.

```bash
python -m mootation.run --show --check python/examples/demo.toml
```

`--check` — смысл всего слоя. Он проверяет, до того как начнётся что-то дорогое, что исполняемый файл каждого шага существует на этой платформе, что `{x[i]}` во входном шаблоне не выходят за `n_vars`, что `bounds` упорядочены и посчитаны, что каждое имя алгоритма есть в реестре и что каждый `pop` удовлетворяет собственному ограничению этого алгоритма: NSGA-III хочет точный размер решётки Das–Dennis, MOEA/D-M2M хочет `pop`, делящийся на `K`. Все претензии сразу, код возврата 1, никакого интерфейса не требуется:

```
3 problem(s):

  - problem.bounds: has 2 entries but n_vars = 3; there must be exactly one [lower, upper] pair per variable
  - problem.steps.solve: executable not found on PATH and not an existing file: 'solver' (platform: linux)
  - algorithms[0] (nsga3): pop = 92 is not a Das-Dennis lattice size for n_objs = 3; nsga3 requires an exact lattice. Nearest attainable: 91, 105
```

Последняя — настоящая ловушка: в таблице I самой статьи про NSGA-III стоит N = 92, ближайшее кратное четырём выше H = 91, а эта библиотека требует размер решётки точно (см. `nsga3.hpp`). Десять секунд здесь вместо десяти минут внутри суточного расчёта.

Команды задаются **массивами** argv, поэтому нечего заключать в кавычки и нечего экранировать, а `run_windows` / `run_linux` / `run_darwin` переопределяют один шаг на одной платформе. Вывод читается одной из пяти стратегий: `csv` по имени столбца, `json` по точечному пути, `regex` для логов солверов (`take = "last"`, потому что солверы печатают значение каждую итерацию), `columns` позиционно и `python:module.function` для HDF5, VTU и всего прочего, что декларативно не описывается.

**Ошибка разбора — это ошибка вычисления.** Ничего не подставляется молча: одна выдуманная точка отравляет архив и все взятые из него метрики. Решает `on_fail` расчёта — `penalty`, `skip` или `abort`.

Два хранилища, намеренно раздельные: рабочее — на воркера и перезаписывается (сетки, VTU, гигабайты); журнал — на расчёт и только дописывается (`{"gen":12,"idx":47,"x":[...],"f":[...],"status":"ok"}`, ~300 байт на вычисление). Возобновление работает от журнала — чтобы знать, что x даёт f, сетка, которая это произвела, не нужна, — и журнал заодно служит кэшем по хешу вектора решений, что важнее, чем звучит: эволюционные алгоритмы часто предлагают одинаковых особей повторно.

**Стандартные наборы** идут в комплекте: ZDT, DTLZ, WFG, MaF, семейство многоугольников Ishibuchi, MOP и BT — 216 задач в 11 семействах, у каждой границы, вычислитель и, где есть замкнутая форма, сэмплер истинного фронта Парето, чтобы у IGD и родственных метрик была настоящая опора. Направьте конфиг на них вместо внешнего солвера:

```toml
[problem]
kind = "builtin"

[benchmarks]
families   = ["DTLZ", "WFG"]
objectives = [3, 5, 10]
runs       = 31
# problems = ["DTLZ2_3D", "WFG4_5D", "MaF3_8D"]   # ... или перечислить поимённо
```

`--check` разворачивает это декартово произведение против реального реестра и называет то, чего не существует, с близкими промахами. `python -m mootation.run --problems` печатает всё. Наборам нужен NumPy; больше здесь он не нужен ничему.

Есть **терминальный интерфейс** над теми же функциями — `python -m mootation.run --tui run.toml` — с четырьмя экранами только для чтения: разрешённый конфиг и вердикт по нему, реестр задач с фильтром, выбранные алгоритмы с возражением каждого по размеру популяции и монитор, читающий журнал вживую. Ему нужен Textual. Он только для чтения намеренно: конфиг вы правите в своём редакторе, потому что конфигурацию, собранную кликами, нельзя ни продиффить, ни скопировать на кластер, ни приложить к статье.

### Сохранение расчёта и его продолжение

```python
res = mootation.minimize(f, bounds, 2, pop_size=100, n_gen=200,
                         save_population="pop.csv",     # что выжило
                         log_evaluations="evals.csv")   # каждый сделанный вызов

# позже — с теми же настройками, или другими, или другим алгоритмом
res = mootation.minimize(f, bounds, 2, algorithm="moead_de", pop_size=91,
                         n_gen=500, seed_population="pop.csv",
                         on_size_mismatch="pad")
```

Оба файла — CSV с преамбулой из `#`, несущей настройки, которые их породили, поэтому `pandas.read_csv(path, comment="#")` читает любой из них напрямую, а популяция загружается обратно как есть. Журнал вычислений хранит каждый вызов, **включая те, что оптимизатор выбросил**, — а для дорогого вычислителя это основная часть стоимости. Оба выключены, пока их не попросят; выключено значит, что файл не открывается и ничего не оборачивается, а не что на каждое вычисление проверяется флаг.

Засев стоит **ноль вычислений целевых функций**: значения читаются из файла, а не пересчитываются.

Это тёплый старт, а не контрольная точка. Ни положение ГПСЧ, ни состояние конкретного алгоритма не сохраняются — только переменные решений, целевые функции и значения ограничений, то есть ровно то, что общее у всех 60 алгоритмов, и потому именно то, что позволяет популяции от NSGA-II засеять расчёт MOEA/D. Возобновлённый расчёт не воспроизводит то, что сделал бы непрерванный; он стартует с того же места.

В C++ это поле, в обеих формах:

```cpp
mootation::Settings s = mootation::Settings::from_file("run.cfg");
s.seed_population  = "pop.csv";                 // или прямо в run.cfg
s.on_size_mismatch = mootation::SizeMismatch::Truncate;

auto r = mootation::run(s, my_evaluator);       // и Session(s) так же
```

либо сразу от предыдущего расчёта, без файла посередине:

```cpp
mootation::Session next(s, mootation::as_population(previous));
```

Посев отвергается — с указанием, что именно не сошлось, — если популяция из другой задачи (другое число переменных или целей) и если расчёт с ограничениями получает популяцию без значений ограничений. Последнее важно: `cv` — это сумма, разобрать её обратно нельзя, и старт с неё посадил бы популяцию, у которой все ограничения читаются как выполненные. Сохранённые файлы несут сами значения (`g1…gk`) именно поэтому. Файловая пара — `mootation::io::save_population` / `load_population`.

### Из других языков (C ABI)

`MOOTATION_BUILD_C_API=ON` собирает разделяемую библиотеку с обычной поверхностью `extern "C"` — мост для ctypes/cffi, P/Invoke, `extern "C"` в Rust, `ccall` в Julia, `loadlibrary` в MATLAB, `iso_c_binding` в Fortran, для чего угодно с FFI. Это единственный компилируемый артефакт, который производит проект.

Границу не пересекает ничего, кроме типов C: конфигурация уходит одной строкой в формате настроек выше, а кандидаты и значения целевых функций ходят плоскими массивами `double` в порядке по строкам. Нет структуры, которую надо держать синхронной между языками, — в этом и смысл.

```c
#include <mootation/capi.h>

moo_session* s = moo_open("algorithm = nsga2\n"
                          "pop_size  = 40\n"
                          "max_gen   = 40\n"
                          "n_vars    = 10\n"
                          "n_objs    = 2\n"
                          "lower     = 0\n"
                          "upper     = 1\n");
int nv = moo_n_vars(s), no = moo_n_objs(s);

for (int n = moo_ask_count(s); n > 0; ) {
    double* x = malloc((size_t)n * nv * sizeof(double));
    double* f = malloc((size_t)n * no * sizeof(double));
    moo_ask(s, x, n * nv);                     /* n строк по nv переменных */
    for (int i = 0; i < n; ++i)
        my_simulator(&x[i * nv], &f[i * no]);
    n = moo_tell(s, f, n * no, NULL, 0);       /* возвращает СЛЕДУЮЩЕЕ число */
    free(x); free(f);
}

int m = moo_result_count(s);                   /* финальная популяция */
/* moo_result(s, x, ..., f, ..., cv, ...); */
moo_close(s);
```

Каждый вызов, который может отказать, возвращает отрицательный int (или `NULL`) и оставляет сообщение в `moo_last_error()`; ни одно исключение не покидает библиотеку. `capi/ctypes_demo.py` гоняет тот же расчёт из Python одним лишь `ctypes` — без шага сборки, без биндинга — и занимает около 60 строк, написанных с расчётом на копирование в любой проект, которому это нужно. `capi/smoke.c` компилируется в CI как C99, поэтому пробравшийся в `capi.h` C++-изм упадёт там, а не в вашем проекте.

В [`capi/wrappers/`](capi/wrappers/) лежит тот же цикл для **Julia**, **R** и **MATLAB/Octave**. Прочитайте README той папки, прежде чем на них полагаться: сам ABI под ними проверяется каждым прогоном CI, но три языковые обёртки писались на машине, где ни один из этих интерпретаторов не установлен, и ни разу не запускались.

### Python

```python
import mootation

def zdt1(x):
    g = 1 + 9 * sum(x[1:]) / (len(x) - 1)
    return [x[0], g * (1 - (x[0] / g) ** 0.5)]

res = mootation.minimize(zdt1, bounds=[(0, 1)] * 10, n_objs=2,
                         algorithm="nsga2", pop_size=100, n_gen=250)
print(res.objectives[0], res.ignored)
```

Ограничения — вторая функция, возвращающая нарушения (`<= 0` означает «выполнено»); `batch=` отдаёт целое поколение разом, для случая дорогого вычисления. `mootation.algorithms()` перечисляет все 60 имён.

**216 тестовых задач** импортируются и решаются любым из алгоритмов, с истинным фронтом Парето там, где есть замкнутая форма:

```python
import mootation.benchmarks as bench

res = bench.solve("DTLZ2_3D", "nsga3", pop_size=91, n_gen=200)
print(bench.igd("DTLZ2_3D", res.objectives))
```

В `python/examples/` лежат пять разобранных скриптов — основы, ограничения, сравнение на наборах, дорогие вычислители, много критериев, — каждый запускаемый и каждый запускаемый в CI. См. [python/examples/README.md](python/examples/README.md).

`res.ignored` перечисляет заданные вами ручки, которых у выбранного алгоритма нет, — скажем, `kappa` у NSGA-II. О них сообщается, а не они отбрасываются, потому что расчёт с молча проигнорированным параметром — не тот расчёт, который вы заказывали.

Для полного контроля `mootation.Problem` / `mootation.Config` / `mootation.run_raw` ложатся на C++ API один в один и ничего не прячут; `minimize` — обёртка над ними, а не другая возможность. (Диспетчеризующая функция называется `run_raw`, потому что `mootation.run` — это подпакет TOML-слоя.)

Сборка из исходников вместо `pip`:

```bash
cmake -S . -B build -DMOOTATION_BUILD_PYTHON=ON && cmake --build build
```

Диспетчеризация порождается из того же `include/mootation/algorithms.def`, который перебирает набор тестов, поэтому биндинг не может разойтись с библиотекой.

### Единый заголовок

Если контроля над путями включения нет — судейская система соревнования, SDK плагинов, ссылка на Compiler Explorer, — `python tools/amalgamate.py` схлопывает библиотеку в один самодостаточный заголовок, вместе с `embed.hpp`. Он порождается, а не коммитится: CI пересобирает его каждый прогон, компилирует отдельно при `-Wall -Wextra -Werror`, проверяет, что `run()` и `Session` и там согласуются, и падает, если в него попал хоть один приватный файл. Комментарии сохраняются — блок в шапке каждого алгоритма и есть смысл библиотеки, а не накладные расходы. Закладывайте около минуты компиляции на каждую единицу трансляции, которая его включает: он несёт все 60 алгоритмов плюс рантайм-диспетчеризацию по ним.

Добавление **своего алгоритма** — это один шаблон класса плюс одна строка в `include/mootation/algorithms.def`; ни базового класса, ни реестра. Контракт, правила слотов и вычислений хранилища и соглашения по шапкам описаны в [docs/writing-an-algorithm.md](docs/writing-an-algorithm.md).

Свои задачи определяются специализацией `Problem<>` для тега-особи (утиный интерфейс: число переменных и критериев, границы по переменным, `calc_objs`) либо подключением `batch_executor` для внешнего/параллельного вычисления. `examples/custom_problem.cpp` — полностью самодостаточный разбор: определяет классическую задачу Kursawe примерно в 40 строк и решает её NSGA-II.

## Задачи о перестановках / упорядочении (например, упаковка)

Для задач, чья естественная кодировка — перестановка (порядок упаковки, расписание, маршрутизация), используйте **кодировку случайными ключами**: держите вещественный геном, а внутри целевой функции декодируйте его как `argsort(keys) → перестановка → жадный декодер` (например, First-Fit для упаковки). Потомки всегда допустимы, и все 60 алгоритмов работают без изменений — это классическая схема BRKGA. Собственные порядковые операторы (OX, вставка, перемешивание) в плане на случаи, где случайные ключи упираются в свой потолок качества.

## План развития

Упорядочено по тому, что снимет больше всего трения, а не по тому, что интереснее делать.

- **Публичный модуль метрик.** Точный гиперобъём уже есть (нарезка HSO), но только приватными копиями внутри `hype`, `sms_m2m` и `hlmea` — единственное число, которое приводит каждая статья, оказалось единственным, которое пользователь посчитать не может. Вынести его, добавить IGD+ и GD+ рядом с `benchmarks.igd`, выставить всё это в Python.
- **Настоящая контрольная точка.** Рестарт с популяции теперь есть везде: `setup_with_seed` в ядре, `seed_population` в `Settings`, а значит в `run`, `Session`, C ABI и Python. Не хватает остального состояния: положение ГПСЧ и внутренний учёт каждого алгоритма не сериализуемы, поэтому трёхсуточная задача, умершая на шестидесятом часу, продолжится с нужного места, но другой траекторией.
- **Встроенный параллельный вычислитель.** `batch_executor` — это крючок; почти каждый пользователь дальше пишет один и тот же пул потоков. `n_workers=8` должен быть параметром.
- **NumPy-нативные сигнатуры в Python.** `minimize` принимает и возвращает списки; массивы на входе и выходе — то, чего ждёт научная экосистема.
- **Запускатель кампаний** (повторные прогоны с зёрнами, сведение IGD/HV в таблицы, Вилкоксон) поверх Python-биндинга.
- **Прогнать обёртки для Julia, R и MATLAB.** Они написаны и лежат в `capi/wrappers/`, но ни один из трёх интерпретаторов не был установлен на машине, где они писались, поэтому маршалинг в этих файлах ни разу не исполнялся. Пока их кто-нибудь не запустит, проверен только ABI под ними.
- Собственные операторы перестановок (порядковое скрещивание, вставка, перемешивание).
- Алгоритм гиперобъёма WFG — более быстрый вариант при большом числе критериев. Пункт про скорость, а не про недостающую возможность.

## Верность источнику и проверка

Заметки о реализации в шапке каждого файла алгоритма документируют: статью (авторы, издание, DOI), схему цикла поколений на 5–8 строк, значения по умолчанию из статьи с указанием раздела, откуда они взяты, и нумерованный список объявленных отклонений. Разрешения внутренних противоречий статьи помечены как таковые и цитируют конфликтующие места, чтобы читатель мог проверить арбитраж, а не принимать его на веру.

Библиотека прошла: построчный двойной слепой аудит против первоисточников с арбитражем разногласий; состязательный проход по опровержению каждой находки, за которым последовала перепроверка самих опровержений (она восстановила существенную их долю); разбор предупреждений компилятора при `/W4 /WX` и `-Wall -Wextra -Werror`; прогоны ASan/UBSan по всем алгоритмам, закреплённые в CI.

Чего этот процесс НЕ даёт: независимого воспроизведения опубликованных экспериментальных результатов. Набор тестов на сходимость в `tests/` проверяет, что каждый алгоритм сходится на DTLZ2 и ZDT1 в пределах грубого допуска, — это дымовой тест, а не воспроизведение бенчмарков. Два алгоритма сейчас несут там пометку `known_issue` (`liu_gu2011`, `moead_m2m`); их шапки объясняют, что именно не разрешено.
